Locks and Correct Critical Sections

Learning objectives

  • State mutual exclusion, progress, and fairness goals.
  • Explain atomic hardware support for locks.
  • Recognize lock-order and granularity tradeoffs.

Read before class

  1. Chapter 28: Locks
    Read for: Mutual exclusion, atomic hardware primitives, spinning, sleeping, fairness, and correctness.
  2. Chapter 29: Lock-based Concurrent Data Structures
    Read for: Protecting invariants in counters, lists, queues, and hash tables; lock granularity.

A lock protects a critical section whose operations must appear indivisible relative to other threads. The programmer must identify the invariant and ensure every access that can violate it follows the same discipline.

Hardware atomic instructions such as test-and-set make it possible to change lock state without an intervening thread observing a half-completed update. Spinning may be appropriate for very short waits but wastes CPU for long waits.

Coarse-grained locks are simpler but reduce parallelism. Fine-grained locks may increase concurrency but also raise proof, ordering, and debugging complexity.

Worked invariant failure: if account fields a and b must sum to 100, locking a -= 10 and b += 10 as two separate critical sections still permits another thread to observe 50 + 40 = 90 between them. Protect the whole transfer, because a correct lock boundary is the span over which the invariant would otherwise be false.

Ordinary flag loads and stores cannot build a correct lock: two threads can both read flag 0 before either writes 1, and both then enter. Test-and-set closes that gap by returning the old value and setting the new value as one atomic hardware operation, so only one contender can observe 0.

Evidence artifact: Code diff plus an invariant-based explanation of why the protected version is correct.

Readiness questions with explanations

Remember What property does a lock primarily provide?
  1. Persistence
  2. Mutual exclusion
  3. Address translation
  4. Disk scheduling

Answer: B. A correctly used lock prevents simultaneous entry into a protected critical section.

Understand Why is an atomic instruction needed to build a basic spin lock?
  1. To update and test lock state indivisibly
  2. To allocate a page
  3. To create a thread
  4. To flush a file

Answer: A. Without an indivisible state transition, two contenders could both believe they acquired the lock.

Source: OSTEP Chapters 28–29: Locks and Lock-based Data Structures

Analyze What is a typical fine-grained locking tradeoff?
  1. Less concurrency and less complexity
  2. More concurrency and more reasoning complexity
  3. No deadlock risk
  4. No shared state

Answer: B. More locks can allow independent operations to overlap but complicate ordering and invariant protection.

Source: OSTEP Chapters 28–29: Locks and Lock-based Data Structures

Remember What code region should a mutex surround?
  1. The critical section that accesses a protected invariant
  2. Every comment
  3. Only process creation
  4. A page-table offset

Hint: Protect the state transition, not an arbitrary line.

Answer: A. All operations that can violate the shared invariant must follow the same lock discipline.

Understand Why can a spin lock waste CPU?
  1. A waiting thread repeatedly checks instead of sleeping
  2. It writes files
  3. It disables registers
  4. It creates page tables

Hint: Consider a long wait on one CPU.

Answer: A. Busy waiting consumes execution cycles while the lock holder runs or is descheduled.

Source: OSTEP Chapter 28; lecture 2-2

Apply A list length and its links must agree. Which locking rule is safest?
  1. Update both while holding the lock that protects the list invariant
  2. Lock only after the update
  3. Use unrelated locks without an order
  4. Rely on sleep

Hint: Readers must never observe a half-updated representation.

Answer: A. The whole invariant-changing transition must be mutually exclusive.

Analyze A lock protects writes but readers access the same variable unlocked. What is wrong?
  1. The protection discipline is incomplete
  2. Readers are always atomic and ordered
  3. The variable becomes persistent
  4. The scheduler fixes it

Hint: A lock is effective only when all participants follow it.

Answer: A. Every conflicting access participating in the invariant needs compatible synchronization.

Evaluate When is a coarse-grained lock a reasonable first design?
  1. When correctness and simplicity dominate and measured contention is acceptable
  2. When no state is shared
  3. When deadlock must be guaranteed
  4. When the lock is never released

Hint: Start from a correct invariant-preserving design.
