Concurrency · Module 7

Threads and Race Conditions

Learning objectives

  • Compare processes and threads.
  • Explain a race as an interleaving of machine operations.
  • Use ThreadSanitizer as evidence, not as a proof of correctness.

Read before class

  1. Chapter 26: Concurrency: An Introduction
    Read for: Thread state, shared address spaces, critical sections, and harmful interleavings.
  2. Chapter 27: Interlude: Thread API
    Read for: pthread creation, joining, arguments, return values, locks, and condition-variable API.

Threads in one process share the address space and open resources but retain separate register state and stacks. This makes communication cheap and also exposes shared data to harmful interleavings.

An expression such as counter++ expands to load, modify, and store operations. Two threads can load the same old value and overwrite one another's updates. The result depends on timing rather than program intent.

A race detector can expose observed conflicts, but one clean run does not prove correctness. Reasoning about which state is shared and which ordering is required remains essential.

Worked lost-update trace: with counter = 50, thread 1 loads 50 and computes 51 before it is interrupted. Thread 2 also loads 50, computes 51, and stores it. Thread 1 resumes and stores its saved 51. Two increments completed, but the shared counter advanced only once because load-add-store was not indivisible.

Hands-on practice

Compile a pthread counter program with and without `-fsanitize=thread`, reproduce a race, then protect the critical section.

Evidence artifact: Before/after output, sanitizer excerpt, and a statement of the protected invariant.

Observe and repair a data race

  1. Expand `counter++` into conceptual load, add, and store operations.
    Evidence: A harmful two-thread interleaving.
  2. Run the unprotected version repeatedly.
    Evidence: Expected and observed totals.
  3. Build with ThreadSanitizer where the host supports it.
    Evidence: A bounded report: finding or platform limitation.
  4. Protect the update with the provided mutex TODO.
    Evidence: Code diff and repeated runs.
  5. State the invariant and why every conflicting access follows one discipline.
    Evidence: An invariant-based correctness argument.

Run: make run

Reflect: Explain why clean test runs alone do not prove the race is absent. This is formative starter work. Read the current Canvas assignment before reusing or submitting any artifact.

Readiness questions with explanations

Understand What do threads in one process normally share?
  1. Every stack frame
  2. Address space and open files
  3. Program counters
  4. CPU registers

Answer: B. Threads share process resources but need independent registers and stacks for independent execution.

Source: OSTEP Chapters 26–27: Concurrency and Thread API

Apply Why can two counter++ operations lose an increment?
  1. The compiler deletes both
  2. Their load/modify/store sequences can overlap
  3. The OS resets the counter
  4. Threads cannot read memory

Answer: B. Both threads may load the same value and then store the same incremented result.

Source: OSTEP Chapters 26–27: Concurrency and Thread API

Analyze A ThreadSanitizer run reports no race. What may be concluded?
  1. The program is proven correct
  2. No race was reported in that explored execution
  3. Locks are unnecessary
  4. The program is deadlock-free

Answer: B. Dynamic testing observes executions; it cannot prove all possible schedules safe.

  1. Process address space

  4. Global variables

Answer: B. Threads share process resources but require individual stacks and registers.

Understand What makes an operation data-racy?
  1. Concurrent conflicting access to shared state without required synchronization
  2. Any use of two local variables
  3. Calling printf once
  4. A deterministic test

Hint: Identify shared location, overlap, and write access.

Answer: A. A data race involves unsynchronized conflicting accesses where at least one is a write.

Source: OSTEP Chapter 26; lecture 2-1

Apply Two threads each execute load counter=4, add one, store. What final value can result?
  1. Exactly 6 only
  2. 5 due to a lost update
  3. 4 only
  4. A page fault necessarily

Hint: Interleave the three machine-level steps.

Answer: B. Both may store 5 after reading 4, losing one logical increment.

Source: OSTEP Chapter 26; lecture 2-1

Analyze Why does adding print statements sometimes hide a race?
  1. The changed timing alters the observed schedule
  2. Printing makes updates atomic by definition
  3. The compiler deletes threads
  4. The race becomes a file link

Hint: Observation can change timing in concurrent programs.

Answer: A. Instrumentation perturbs timing and may make a harmful interleaving less likely without fixing it.

Source: OSTEP Chapter 26; lecture 2-1

Evaluate Which claim about a race fix is strongest?
  1. It passed once
  2. The shared invariant is protected on every access and stress/sanitizer evidence agrees
  3. The output looked plausible
  4. The program runs faster

Hint: Combine an invariant argument with observations.

Answer: B. Correctness reasoning plus dynamic evidence is stronger than either a single run or a tool alone.
