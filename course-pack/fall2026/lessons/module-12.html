Persistence · Module 12

Files, Directories, and Metadata

Learning objectives

  • Relate descriptors, open-file state, and inodes.
  • Explain hard links and symbolic links.
  • Use metadata to reason about names and objects.

Read before class

  1. Chapter 39: Files and Directories
    Read for: File descriptors, open/read/write, directories, links, metadata, permissions, mounting, and fsync.

A file descriptor is a per-process handle returned by open; it refers through kernel state to an underlying file object and current offset. A pathname is resolved through directories and is not itself the file's content identity.

Directory entries map names to underlying objects such as inodes. Hard links create another directory entry for the same inode; symbolic links store a pathname to resolve later.

Metadata operations such as stat help separate questions about names, sizes, permissions, link counts, and timestamps.

Worked link-count trace: creating original gives its inode one name; ln original hard raises the same inode's link count to two; ln -s original symbolic creates a separate inode that stores the pathname. Removing original leaves hard able to read the data but makes symbolic dangle. Data is reclaimed only after the link count is zero and no process still holds it open.

Two independent open calls can reach the same inode through separate open-file entries and therefore keep separate offsets. Descriptors created by dup or inherited across fork share an open-file entry and its offset, so a read through one advances the position observed by the other.

Understand What is a file descriptor?
  1. A pathname stored on disk only
  2. A process-local handle to kernel-managed open-file state
  3. A physical disk sector
  4. A scheduler queue

Answer: B. The integer descriptor indexes per-process state that refers to an open file or I/O object.

Apply Two hard-link names usually refer to what?
  1. Different inodes with copied data
  2. The same underlying inode
  3. Two processes
  4. A TLB entry

Answer: B. A hard link adds another directory entry referring to the same inode.

Analyze Why can an open file remain readable after its last pathname is removed?
  1. The open kernel reference still retains the object
  2. The TLB restores the name
  3. The compiler caches it forever
  4. Removing names never changes metadata

Answer: A. The data object is reclaimed only when link and active reference conditions allow it.

  1. Both directory entries refer to the same underlying object
  2. They are symbolic links necessarily
  3. The shell copied the file contents

Answer: A. A hard link adds another name-to-inode mapping rather than another file object.

Apply After deleting one of two hard links, what normally happens to the file data?
  1. It remains reachable through the other hard link
  2. It must vanish immediately
  3. It becomes a process
  4. It moves to the TLB

Hint: Deletion removes a directory entry first.

Answer: A. Removing one name decrements the link count; the object remains while another link/open reference exists.

Analyze A symbolic link breaks after its target is renamed. Why?
  1. It stores a pathname that no longer resolves
  2. It stores the same inode directly
  3. It pins the target open forever

Answer: A. A symlink contains a path, so later resolution can fail after a rename or removal.
