Virtualization · Module 1

What an Operating System Does

Learning objectives

  • Explain virtualization, concurrency, and persistence as the course's three organizing ideas.
  • Distinguish mechanism from policy.
  • Use a Unix shell, compiler, and debugger safely.

Prepare: OSTEP Introduction and Chapter 2: Introduction to Operating Systems

An operating system turns physical resources into easier abstractions while coordinating protection and sharing. CPU virtualization creates the process abstraction; memory virtualization gives each process an address space; persistence organizes durable data behind files and directories.

Mechanism answers how an operation can happen—for example, a context switch. Policy answers which choice to make—for example, which ready process runs next. Keeping the two separate makes later scheduler and memory-management designs easier to compare.

The hands-on path uses C, a shell, Docker, Make, and eventually xv6. The goal of the first lab is reproducibility: another student should be able to build and run the same small program from the same workspace.

Hands-on practice

Create the portable OS lab workspace, inspect its container recipe, compile the starter C program, and record the compiler/runtime versions.

Evidence artifact: A short environment report containing the commands used, versions, output, and one troubleshooting note.

Readiness questions with explanations

Understand Which example is a policy rather than a mechanism?
  1. Saving CPU registers during a context switch
  2. Choosing the next ready process
  3. Entering kernel mode on a trap
  4. Translating a virtual address

Answer: B. Choosing among runnable processes is a scheduling policy. Saving/restoring state and entering the kernel are mechanisms.

Apply A program builds on one laptop but not another. What is the best first reproducibility step?
  1. Rewrite the program
  2. Record tool versions and build commands
  3. Increase CPU priority
  4. Disable compiler warnings

Answer: B. A versioned environment and repeatable command are needed before diagnosing code differences.

Analyze Which mapping correctly pairs the course themes?
  1. CPU→persistence; files→concurrency
  2. Processes→virtualization; races→concurrency; files→persistence
  3. Locks→virtualization; pages→persistence
  4. Directories→concurrency; threads→persistence

Answer: B. Processes/address spaces are virtual abstractions, shared execution introduces concurrency, and file systems provide persistence.

Virtualization · Module 2

Processes and Process APIs

Learning objectives

  • Describe process state and address-space contents.
  • Trace fork, exec, wait, and exit.
  • Explain how a shell builds a process pipeline.

Prepare: OSTEP Chapters 4–5: Processes and Process API

A process is a running program plus the state needed to resume it: address space, registers, open-file information, credentials, and scheduling state. The operating system assigns a process identifier and tracks transitions such as ready, running, and blocked.

fork creates a child process with a logically separate address space; its return value distinguishes parent from child. exec replaces the calling process image with another program. wait lets a parent synchronize with child termination, and exit releases the process.

The separation of fork and exec gives a shell a useful setup window: after fork and before exec, the child can redirect file descriptors or construct a pipeline.

Hands-on practice

Write a small C program that forks, prints parent/child PIDs, waits, and then add an exec call. Predict the output before running it.

Evidence artifact: Annotated process tree plus predicted and observed output; explain every difference without copying assignment answers.

Readiness questions with explanations

Remember What does fork return in the newly created child?
  1. The parent PID
  2. Zero
  3. Negative one
  4. The child PID

Answer: B. A successful fork returns zero in the child and the child PID in the parent.

Understand What does exec do to the calling process?
  1. Creates a second process
  2. Replaces its program image
  3. Blocks until a child exits
  4. Duplicates every open file

Answer: B. exec loads a new program into the current process; it does not create another process.

Analyze Why is fork followed by exec useful to a shell?
  1. The parent can change the child after exec
  2. The child can set redirection before replacing its image
  3. exec automatically waits
  4. fork prevents context switches

Answer: B. The child configures descriptors and environment between fork and exec, enabling redirection and pipelines.

Virtualization · Module 3

CPU Mechanisms and Scheduling

Learning objectives

  • Explain limited direct execution and timer interrupts.
  • Compute turnaround, response, and waiting time.
  • Compare FCFS, SJF, STCF, RR, and MLFQ tradeoffs.

Prepare: OSTEP Chapters 6–10: Mechanism and CPU Scheduling

Limited direct execution lets user code run directly on the CPU while privileged operations trap into the kernel. A periodic timer interrupt ensures the OS can regain control even when a process does not cooperate.

Schedulers balance different goals. Turnaround time measures completion latency, response time measures time until first run, and fairness concerns how service is shared. A policy that optimizes one workload can harm another.

MLFQ approximates knowledge of job behavior by observing CPU use. Interactive jobs tend to remain at higher priority; CPU-intensive jobs move downward. Priority boosts prevent indefinite starvation.

Hands-on practice

Run OSTEP scheduling simulators with at least three seeds. Draw one Gantt chart manually, then reconcile it with simulator output.

Evidence artifact: Gantt chart, metric calculations, simulator command, and a short policy tradeoff paragraph.

Readiness questions with explanations

Understand Why does an OS need a timer interrupt?
  1. To allocate disk blocks
  2. To regain CPU control from a running process
  3. To translate addresses
  4. To create a file descriptor

Answer: B. The timer provides a non-cooperative path back into the kernel so the scheduler can preempt.

Apply Jobs A(3) and B(1) arrive together. Under non-preemptive SJF, which order minimizes average turnaround?
  1. A then B
  2. B then A
  3. Either is identical
  4. They must alternate

Answer: B. Running the shortest job first completes B at 1 and A at 4, reducing average completion time.

Analyze What MLFQ mechanism primarily addresses starvation?
  1. Longer process names
  2. Periodic priority boosts
  3. Disabling preemption
  4. One global time quantum only

Answer: B. Boosting waiting jobs returns them to a higher-priority queue so they eventually receive service.

Virtualization · Module 4

Address Spaces, Relocation, and Segmentation

Learning objectives

  • Identify code, data, heap, and stack.
  • Translate addresses with base and bounds.
  • Analyze fragmentation and segmented growth.

Prepare: OSTEP Chapters 13–16: Address Spaces through Segmentation

An address space is the process-visible arrangement of code, static data, heap, stack, and mapped regions. Virtual addresses must be translated and checked before physical memory is accessed.

Dynamic relocation adds a base to a virtual offset and checks the result against a bound. The hardware performs the fast check; the OS controls base/bounds values during context switches.

Segmentation represents logically different regions with separate bases, limits, and growth directions. It improves flexibility but introduces external fragmentation and placement questions.

Hands-on practice

Use the OSTEP relocation and segmentation simulators. For three addresses, compute the result by hand before revealing the simulator answer.

Evidence artifact: Translation table with validity decision, arithmetic, and physical address or protection fault.

Readiness questions with explanations

Remember Which region normally grows as dynamic allocation occurs?
  1. Code
  2. Heap
  3. Program counter
  4. Page table register

Answer: B. malloc-family allocation typically expands or maps heap storage.

Apply With base 4000 and bound 500, what happens to virtual address 300?
  1. Fault
  2. Physical 3700
  3. Physical 4300
  4. Physical 4500

Answer: C. 300 is within the 500-byte bound, so translation is base + offset = 4300.

Analyze What is a main cost of variable-sized segmentation?
  1. No protection
  2. External fragmentation
  3. No sharing
  4. Every access causes a disk read

Answer: B. Variable-sized segments leave noncontiguous holes that can make allocation difficult.

Virtualization · Module 5

Paging, TLBs, and Page Tables

Learning objectives

  • Split a virtual address into VPN and offset.
  • Explain TLB hits and misses.
  • Compare linear and multi-level page tables.

Prepare: OSTEP Chapters 18–20: Paging, TLBs, and Page Tables

Paging divides virtual and physical memory into fixed-size pages and frames. The offset is preserved during translation; a page-table entry supplies the physical frame number and protection metadata.

A translation lookaside buffer caches recent translations. A TLB hit avoids a page-table lookup, while a TLB miss invokes hardware or OS-assisted page-table traversal. A TLB miss is not automatically a page fault.

Linear page tables are simple but can consume substantial memory. Multi-level tables allocate lower levels only for populated virtual regions, trading extra lookup steps for space savings.

Hands-on practice

Use the OSTEP paging translation simulator, then write a tiny address-translation worksheet that labels VPN, offset, valid bit, and PFN.

Evidence artifact: Completed translations plus one paragraph distinguishing a TLB miss, invalid PTE, and page fault.

Readiness questions with explanations

Apply With 4 KiB pages, how many offset bits are in a byte address?
  1. 4
  2. 10
  3. 12
  4. 16

Answer: C. 4 KiB is 4096 = 2^12 bytes, so the offset uses 12 bits.

Understand Which statement is correct?
  1. Every TLB miss is a page fault
  2. A TLB caches virtual-to-physical translations
  3. The page offset changes during translation
  4. Paging creates external fragmentation between frames

Answer: B. A TLB is a translation cache. Missing there may still find a valid in-memory page-table entry.

Analyze Why can a multi-level page table use less memory?
  1. It removes offsets
  2. It omits lower-level tables for unused regions
  3. It stores pages on the CPU
  4. It disables protection bits

Answer: B. Sparse address spaces need only the page-table subtrees that describe mapped regions.

Virtualization · Module 6

Demand Paging and Replacement

Learning objectives

  • Trace a page fault from trap to restart.
  • Compare FIFO, OPT, LRU, and Clock.
  • Reason about locality and thrashing.

Prepare: OSTEP Chapters 21–22: Beyond Physical Memory and Replacement

Demand paging leaves some virtual pages outside physical memory. Accessing a nonresident valid page traps to the OS, which locates data, chooses a frame, performs I/O if needed, updates metadata, and restarts the instruction.

Replacement policy decides which resident page to evict. OPT is an unattainable benchmark, LRU exploits recency, FIFO is simple, and Clock approximates recency with reference bits.

Locality makes caching effective. When a workload's actively used pages exceed available memory, repeated eviction and reload can cause thrashing.

Hands-on practice

Run page-replacement traces under FIFO, LRU, and Clock; explain one point where policies diverge.

Evidence artifact: Frame-by-frame table, page-fault counts, and a locality-based explanation.

Readiness questions with explanations

Understand What distinguishes a page fault from a TLB miss?
  1. A page fault means the referenced page is not currently resident or access is invalid
  2. A TLB miss always terminates the process
  3. A page fault never enters the kernel
  4. They are identical

Answer: A. A TLB miss concerns the translation cache; a page fault concerns page-table validity/residency or protection.

Remember Why is OPT mainly a benchmark?
  1. It requires future references
  2. It cannot count faults
  3. It uses no memory
  4. It is identical to FIFO

Answer: A. OPT evicts the page whose next use is farthest in the future, information a real system does not possess.

Analyze What pattern best signals thrashing?
  1. High CPU use and no faults
  2. Frequent faults with little useful execution
  3. One compulsory miss at startup
  4. A large TLB

Answer: B. Thrashing spends much of the time moving pages rather than running useful instructions.

Concurrency · Module 7

Threads and Race Conditions

Learning objectives

  • Compare processes and threads.
  • Explain a race as an interleaving of machine operations.
  • Use ThreadSanitizer as evidence, not as a proof of correctness.

Prepare: OSTEP Chapters 26–27: Concurrency and Thread API

Threads in one process share the address space and open resources but retain separate register state and stacks. This makes communication cheap and also exposes shared data to harmful interleavings.

An expression such as counter++ expands to load, modify, and store operations. Two threads can load the same old value and overwrite one another's updates. The result depends on timing rather than program intent.

A race detector can expose observed conflicts, but one clean run does not prove correctness. Reasoning about which state is shared and which ordering is required remains essential.

Hands-on practice

Compile a pthread counter program with and without `-fsanitize=thread`, reproduce a race, then protect the critical section.

Evidence artifact: Before/after output, sanitizer excerpt, and a statement of the protected invariant.

Readiness questions with explanations

Understand What do threads in one process normally share?
  1. Every stack frame
  2. Address space and open files
  3. Program counters
  4. CPU registers

Answer: B. Threads share process resources but need independent registers and stacks for independent execution.

Apply Why can two counter++ operations lose an increment?
  1. The compiler deletes both
  2. Their load/modify/store sequences can overlap
  3. The OS resets the counter
  4. Threads cannot read memory

Answer: B. Both threads may load the same value and then store the same incremented result.

Analyze A ThreadSanitizer run reports no race. What may be concluded?
  1. The program is proven correct
  2. No race was reported in that explored execution
  3. Locks are unnecessary
  4. The program is deadlock-free

Answer: B. Dynamic testing observes executions; it cannot prove all possible schedules safe.

Concurrency · Module 8

Locks and Correct Critical Sections

Learning objectives

  • State mutual exclusion, progress, and fairness goals.
  • Explain atomic hardware support for locks.
  • Recognize lock-order and granularity tradeoffs.

Prepare: OSTEP Chapters 28–29: Locks and Lock-based Data Structures

A lock protects a critical section whose operations must appear indivisible relative to other threads. The programmer must identify the invariant and ensure every access that can violate it follows the same discipline.

Hardware atomic instructions such as test-and-set make it possible to change lock state without an intervening thread observing a half-completed update. Spinning may be appropriate for very short waits but wastes CPU for long waits.

Coarse-grained locks are simpler but reduce parallelism. Fine-grained locks may increase concurrency but also raise proof, ordering, and debugging complexity.

Hands-on practice

Implement a mutex-protected counter, then deliberately move one access outside the critical section and explain the broken invariant.

Evidence artifact: Code diff plus an invariant-based explanation of why the protected version is correct.

Readiness questions with explanations

Remember What property does a lock primarily provide?
  1. Persistence
  2. Mutual exclusion
  3. Address translation
  4. Disk scheduling

Answer: B. A correctly used lock prevents simultaneous entry into a protected critical section.

Understand Why is an atomic instruction needed to build a basic spin lock?
  1. To update and test lock state indivisibly
  2. To allocate a page
  3. To create a thread
  4. To flush a file

Answer: A. Without an indivisible state transition, two contenders could both believe they acquired the lock.

Analyze What is a typical fine-grained locking tradeoff?
  1. Less concurrency and less complexity
  2. More concurrency and more reasoning complexity
  3. No deadlock risk
  4. No shared state

Answer: B. More locks can allow independent operations to overlap but complicate ordering and invariant protection.

Concurrency · Module 9

Condition Variables and Semaphores

Learning objectives

  • Use condition variables with a predicate and mutex.
  • Distinguish mutual exclusion from condition synchronization.
  • Model counting and binary semaphores.

Prepare: OSTEP Chapters 30–31: Condition Variables and Semaphores

A condition variable lets a thread sleep until shared state may satisfy a predicate. The thread checks that predicate while holding the associated mutex and waits in a loop because wakeups do not guarantee the condition is now true.

A semaphore combines a counter with atomic wait and post operations. A counting semaphore can represent available units of a resource; a binary semaphore can resemble a lock, though ownership conventions differ.

Correct synchronization begins with state and invariants, not with choosing a primitive. First state what must be true; then choose locks, conditions, or semaphores that enforce it.

Hands-on practice

Build a bounded-buffer or ordered-print exercise with pthread mutexes and condition variables; add a log that makes waiting and wakeup visible.

Evidence artifact: State diagram, predicate, code, and trace explaining each wait/signal.

Readiness questions with explanations

Apply How should a condition-variable wait normally be guarded?
  1. By an if with no lock
  2. By a while loop checking the predicate under the mutex
  3. By sleeping for a fixed time
  4. By a page fault

Answer: B. The predicate must be rechecked after wakeup while the mutex protects the shared state.

Understand What can a counting semaphore represent?
  1. Only a Boolean
  2. The number of available identical resources
  3. A virtual address
  4. A process identifier

Answer: B. Its count can track multiple available units; wait consumes one and post returns one.

Analyze Why is a timed sleep a weak substitute for synchronization?
  1. Time never advances
  2. It guesses about another thread rather than observing protected state
  3. It always deadlocks
  4. It prevents compilation

Answer: B. Timing varies across executions; synchronization must encode the actual condition or ordering.

Concurrency · Module 10

Deadlock and Liveness

Learning objectives

  • Identify the four Coffman conditions.
  • Draw a wait-for graph.
  • Compare prevention, avoidance, detection, and recovery.

Prepare: OSTEP Chapter 32: Common Concurrency Problems

Deadlock is a liveness failure in which participants wait forever for resources held within the waiting set. The classic necessary conditions are mutual exclusion, hold-and-wait, no preemption, and circular wait.

A consistent global lock order prevents cycles. Other strategies remove a different necessary condition, avoid unsafe allocations, detect cycles after they form, or recover by terminating or rolling back work.

Not every hang is deadlock. Starvation denies service to one participant while the system still progresses; livelock changes state repeatedly without useful progress.

Hands-on practice

Create a two-lock deadlock under controlled conditions, capture thread stacks, then repair it with a documented lock order.

Evidence artifact: Wait-for graph, stack evidence, fixed code, and a deadlock/starvation/livelock comparison.

Readiness questions with explanations

Remember Which is one Coffman condition?
  1. Circular wait
  2. Demand paging
  3. Spatial locality
  4. Write buffering

Answer: A. Circular wait is one of the four necessary conditions for deadlock.

Apply Threads acquire locks only in increasing numeric order. Which condition is targeted?
  1. Mutual exclusion
  2. Circular wait
  3. No preemption
  4. Persistence

Answer: B. A total order prevents a cycle in resource acquisition.

Analyze The system keeps running, but one thread never gets the lock. What is this?
  1. Deadlock necessarily
  2. Starvation
  3. A page fault
  4. Journaling

Answer: B. Progress by others with indefinite denial to one participant is starvation.

Persistence · Module 11

I/O Devices and Device Interaction

Learning objectives

  • Explain polling, interrupts, and DMA.
  • Trace an I/O request across user/kernel/device boundaries.
  • Recognize why device latency changes OS policy.

Prepare: OSTEP Chapter 36: I/O Devices

Programs access devices through OS abstractions and system calls. The kernel validates requests, coordinates drivers, and arranges data transfer while preserving isolation.

Polling repeatedly checks device status; interrupts let the CPU do other work until notification; DMA moves bulk data between device and memory with limited CPU copying. Each approach has workload-dependent overheads.

A correct I/O trace distinguishes request submission, waiting/blocking, device completion, interrupt handling, and process wakeup.

Hands-on practice

Use `strace` in the container to observe open/read/write calls from a small C program; annotate which operations cross into the kernel.

Evidence artifact: Filtered trace, annotated request path, and one performance hypothesis.

Readiness questions with explanations

Understand What is a principal benefit of DMA?
  1. It removes files
  2. It transfers bulk data without CPU copying every word
  3. It prevents all interrupts
  4. It replaces virtual memory

Answer: B. The CPU programs the transfer, and the DMA engine handles much of the data movement.

Analyze When can polling be reasonable?
  1. A device is expected to complete almost immediately
  2. A device takes minutes and CPU work is plentiful
  3. There is no status register
  4. The process has exited

Answer: A. For very short waits, polling can cost less than sleeping and handling an interrupt.

Apply Which tool can show a Linux program's file-related system calls?
  1. strace
  2. make clean only
  3. A page-table simulator
  4. The linker alone

Answer: A. strace records system-call entry, arguments, and results, making the user/kernel boundary visible.

Persistence · Module 12

Files, Directories, and Metadata

Learning objectives

  • Relate descriptors, open-file state, and inodes.
  • Explain hard links and symbolic links.
  • Use metadata to reason about names and objects.

Prepare: OSTEP Chapter 39: Files and Directories

A file descriptor is a per-process handle returned by open; it refers through kernel state to an underlying file object and current offset. A pathname is resolved through directories and is not itself the file's content identity.

Directory entries map names to underlying objects such as inodes. Hard links create another directory entry for the same inode; symbolic links store a pathname to resolve later.

Metadata operations such as stat help separate questions about names, sizes, permissions, link counts, and timestamps.

Hands-on practice

Create a file, hard link, and symbolic link inside the lab workspace; compare `ls -li`, `stat`, and behavior after removing the original name.

Evidence artifact: Command transcript and an inode/name diagram explaining every observation.

Readiness questions with explanations

Understand What is a file descriptor?
  1. A pathname stored on disk only
  2. A process-local handle to kernel-managed open-file state
  3. A physical disk sector
  4. A scheduler queue

Answer: B. The integer descriptor indexes per-process state that refers to an open file or I/O object.

Apply Two hard-link names usually refer to what?
  1. Different inodes with copied data
  2. The same underlying inode
  3. Two processes
  4. A TLB entry

Answer: B. A hard link adds another directory entry referring to the same inode.

Analyze Why can an open file remain readable after its last pathname is removed?
  1. The open kernel reference still retains the object
  2. The TLB restores the name
  3. The compiler caches it forever
  4. Removing names never changes metadata

Answer: A. The data object is reclaimed only when link and active reference conditions allow it.

Persistence · Module 13

File-System Implementation and Crash Consistency

Learning objectives

  • Map a pathname to inode and data blocks.
  • Explain allocation structures and caching.
  • Reason about journaling order after a crash.

Prepare: OSTEP Chapters 40–42: File-System Implementation, FFS, and Crash Consistency

A simple file system divides storage among metadata, allocation structures, inodes, directories, and data blocks. Reading a pathname can require a sequence of directory and inode lookups before reaching content blocks.

FFS-style placement tries to preserve locality by grouping related metadata and data. Caching and write buffering reduce I/O but create ordering questions when memory state is lost during a crash.

Journaling records an update transaction so recovery can distinguish committed work from incomplete work. Correctness depends on what is logged and on enforced write ordering, not merely on issuing writes.

Hands-on practice

Walk a simplified VSFS image or diagram: resolve a pathname, identify inode/data bitmap changes for file creation, then mark crash points in an update sequence.

Evidence artifact: Block-access trace and crash-consistency table showing states before commit, after commit, and after checkpoint.

Readiness questions with explanations

Apply Creating a new regular file typically changes which structures?
  1. Only the CPU scheduler
  2. A directory, an inode allocation structure, and inode metadata
  3. Only the TLB
  4. Only the process stack

Answer: B. Creation allocates/initializes metadata and connects a directory name to it; data blocks may be allocated when content is written.

Understand What problem does journaling primarily address?
  1. CPU fairness
  2. Consistency after interrupted multi-step updates
  3. Virtual-address size
  4. Thread creation speed

Answer: B. A crash can interrupt related writes; the journal provides a recoverable transaction boundary.

Analyze Why is write ordering important even with a journal?
  1. Recovery assumptions depend on commit/data reaching storage in the intended order
  2. Disks execute C code
  3. Page offsets must change
  4. It prevents all hardware failure

Answer: A. If storage reorders writes, a commit record may become durable before required log data unless barriers/order are enforced.
